# Implementation Plan: Install and Run With the CLI

**Spec**: [spec.md](spec.md) | **Research**: [research.md](research.md) |
**Contract**: [CLI commands](contracts/cli-commands.md)

## Summary

A new `cli/` workspace builds the `your-space` command. It works on the installation in the current
folder: `init` downloads the release files for its own version, checks them and writes `.env`;
`start` checks the engine and ports, runs Compose, creates the owner through the server's own
command and prints a summary. Every other command wraps Compose or a server command the same way.
The CLI keeps no state of its own and never calls Your Space's HTTP API.

It is published four ways from one bundle: an npm package, a standalone Linux executable for ARM
and Intel built with Node's own single-executable feature, and `.deb` and `.rpm` packages built with
the distributions' own tools.

## Technical Context

- **Language and runtime**: TypeScript on Node.js 26, as in journeys 001 and 002. The npm package
  runs on Node.js 22 or newer, since people who run it with `npx` bring their own Node.
- **Existing stack**: the release files from journey 001 (`compose.yaml`, `stack.yaml`, `modes/`,
  `env.example`), the server's operator commands, Docker Compose 2.26 or newer.
- **Engine**: any Docker-compatible engine on this machine that Docker's own client reaches.
- **Target**: Linux, ARM and Intel, in this journey. macOS runs the npm package until the macOS and
  Windows pass.

## Constitution Check

| Principle | How this plan meets it |
| --- | --- |
| I. Platform and apps independent | The CLI is part of the platform repository and touches no app code. |
| II. User control and hosting choice | The CLI writes only the `.env` lines the person's answers need, the same lines the guide documents. Every question has a default or a flag; secrets stay generated by Your Space. Nothing opens to the network without the person choosing a domain. |
| III. Identity, permissions, ownership | The CLI's authority is access to the machine, as the server's commands already are. It has no sign-in and stores no credentials ([spec](spec.md#client-and-cli)). |
| IV. Apps directly installable | Unchanged. |
| V. Protect private data | Secrets and set-password tokens are printed only by the commands that exist to show them, and never logged. The CLI sends nothing anywhere but GitHub's release downloads. |
| VI. Proportionate discipline | Each command has unit tests for its logic and an end-to-end test against a real stack; the domain flow runs against Let's Encrypt's test authority. |
| VII. Reuse before building | Commander parses commands, with its own help, version, errors and exit handling; Clack asks questions and shows progress with its own prompts, spinners, logs and notes. Neither is wrapped or extended (constitution 1.4.1). Compose, the Docker CLI and the server's commands do the work; Node's built-ins download, check and resolve names. Two runtime dependencies, both bundled. |
| VIII. Concepts, not technologies | Commands work with an installation, an engine connection, a setup and server commands ([spec](spec.md#concepts-and-adapters)); `cli/src/compose.ts` and `cli/src/engine.ts` are the only modules that run Docker. |

## Architecture

```text
your-space (cli/)
  commands ──► installation (folder: release files, .env)
           ├─► engine      ──► docker version / info / context        (Docker CLI)
           ├─► compose     ──► docker compose up / stop / ps / logs   (in the folder)
           ├─► server      ──► docker compose exec -T server <command> --json
           └─► checks      ──► ports (TCP), DNS (node:dns), certificate (TLS to 127.0.0.1:443)
  release  ──► https://github.com/your-space-ai/your-space/releases/download/v<version>/
               your-space.tar.gz + SHA256SUMS                          (fetch, node:crypto, tar)
```

Compose is run in the installation's folder with no `-f` or `-p`, so it reads `compose.yaml` and
`.env` exactly as `docker compose` does when a person runs it there. The project name stays
`your-space`, set in `compose.yaml`, so there is one installation per engine
([research R9](research.md#r9-one-installation-per-engine)).

### Modules

| Module | What it does |
| --- | --- |
| `cli/src/index.ts` | The program: commands, global options (`--workdir`, `--json`, `--verbose`), exit statuses. |
| `cli/src/ui.ts` | Output for people (Clack: questions, spinners, notes) and for scripts (one JSON object per command on stdout). Questions without a terminal fail naming their flag. |
| `cli/src/errors.ts` | `CliError` with an exit status and a message in Your Space's terms; Compose's and the engine's own output is attached for `--verbose`. |
| `cli/src/installation.ts` | Finds and reads an installation: its files, `.env`, version and setup. |
| `cli/src/env-file.ts` | Reads `.env` and sets or clears one line, keeping comments and the person's own lines. |
| `cli/src/release.ts` | Downloads a release's files and checksums, checks them, unpacks them. |
| `cli/src/engine.ts` | The engine connection: reachability, versions, processor, socket path. |
| `cli/src/compose.ts` | Runs Compose in the folder: up, stop, ps, logs, run, exec. |
| `cli/src/server.ts` | Runs the server's commands with `--json` and returns their result and exit status. |
| `cli/src/checks.ts` | Ports, DNS for a domain, the certificate for a domain, and what Caddy logged about it. |
| `cli/src/setup.ts` | The setup questions shared by `init` and `configure`, and the `.env` lines they produce. |
| `cli/src/summary.ts` | The summary `start` and `status` print: address, setup, services, engine, apps, names to forward. |
| `cli/src/secrets.ts` | Replacing a secret and starting with new ones: the guide's steps in order. |
| `cli/src/commands/*.ts` | One file per command: `init`, `start`, `stop`, `status`, `logs`, `owner`, `secrets`, `configure`. |

### Server change

One new operator command, `show-owner [--json]`, reports whether there is an owner, and their
username and name. `start` needs it to decide whether to create the
owner, and none of the existing commands answers it without side effects (`reset-link` cancels an
earlier link). It follows the
[operator commands contract](../001-workspace-owner-access/contracts/operator-commands.md)'s output
and exit codes.

### Release

The release workflow gains a `cli` job and a shared script:

- `deploy/release-files.sh <version> <out>` makes `your-space.tar.gz` as the workflow did, now used
  by the browser tests too. It fixes the image count check, which still expected three images after
  journey 002 added the runtime manager.
- `cli/scripts/build.mjs` bundles the CLI with esbuild into `cli/dist/your-space.cjs`, with its
  version and its dependencies inside.
- `cli/scripts/executable.sh <arch>` builds the standalone executable with `node --build-sea`, using
  the official Node.js binary for that processor, checked against Node's published checksums, so one
  Intel runner builds both.
- `cli/scripts/packages.sh <arch>` builds `.deb` with `dpkg-deb` and `.rpm` with `rpmbuild`.
- The workflow uploads the executables, packages and tarball with one `SHA256SUMS` file, and
  stages the npm package with npm trusted publishing (GitHub OIDC), with no stored token, for a maintainer to approve.

### Dependencies

| Dependency | Where | Why | Alternatives |
| --- | --- | --- | --- |
| [Commander](https://github.com/tj/commander.js) (MIT) | CLI, bundled | Commands, options, help and version, with no dependencies of its own | yargs (larger API), oclif (a framework, plugins and a generator we don't need), Node's `util.parseArgs` (no subcommands or help) |
| [@clack/prompts](https://github.com/bombshell-dev/clack) (MIT) | CLI, bundled | Questions, spinners, step logs and boxed notes in one package, for Supabase-like output | Inquirer (questions only; spinners need another package) |
| [esbuild](https://esbuild.github.io) (MIT) | Build | Bundles the CLI into one file for npm and the executable. Already in the lockfile through Vite and tsx | Rolldown (newer), tsc (doesn't bundle) |
| Node.js single executable (`--build-sea`) | Build | The standalone executable, with no new tool | Bun or Deno compile (another runtime), `pkg` (archived) |
| `dpkg-deb`, `rpmbuild` | Release workflow | The distributions' own packagers; on Ubuntu runners or one apt package | nfpm (smaller project), fpm (needs Ruby) |
| System `tar` | CLI at run time | Unpacks the release tarball; present on every Linux and macOS machine | The `tar` npm package |
| [Pebble](https://github.com/letsencrypt/pebble) (MPL-2.0) | Tests only | Let's Encrypt's own test certificate authority, so the domain flow is tested end to end | A real domain (can't run in CI) |

## Testing

- **Unit** (`cli/tests/*.test.ts`, Vitest): `.env` editing, release checks, version and engine
  parsing, the socket path, the summary for each setup, Caddy log reading, DNS check results, JSON
  output and exit statuses.
- **Server** (`server/tests/show-owner.test.ts`): the new command against the test database.
- **End to end** (`e2e/tests/cli.spec.ts`, Chromium only, like the setups checks): the CLI against a
  real stack built from this repository. The test builds the release files with
  `deploy/release-files.sh`, tags the locally built images with the CLI's version so Compose doesn't
  pull them, and serves the release from a local web server (`YS_E2E_RELEASES`). It covers `init`
  and `start` to signing in, `status`, `stop` and `start` with an app, `logs`, `owner reset-link`,
  `secrets`, `configure`, a taken port, a folder installed by hand, another Docker context, and a
  domain with HTTPS from Pebble.
- **Packaging**: CI builds the executable and the packages, installs the `.deb` and runs
  `your-space --version`; the end-to-end test runs the executable when `YS_E2E_CLI` names it.
