# Journey 008 · Open Your Space on a Mac

**First desktop build for private review.** The release is ready when an owner can download a signed Mac app, open it from Finder and choose **Run on this Mac** or **Connect to a server**. Both paths end in the existing Your Space dashboard, where the owner reviews and installs an app using its installation kit.

This slice uses an owner-installed Docker-compatible engine for local workspaces and Electron for the Mac client. A bundled engine, native views for each installed app, other desktop platforms and PWA installation remain later roadmap work. The Mac app updates itself, and quitting it stops the local workspace it started (2026-11-23); a server workspace keeps running and owns its jobs when the app quits. [Architecture decisions](../../docs/architecture/decisions.md) · [Roadmap](../../docs/roadmap.md)

## What the owner does

**Run on this Mac.** The app shows which Docker engine it detected. If Docker or Compose is missing, stopped, inaccessible or too old, explain the specific problem, show the supported Mac engine choices and link to setup guidance and offer **Check again**. The owner installs or starts their chosen engine. The owner can return to the server path while Docker detection runs. [Installation guide](../../docs/install/index.md)

The owner can accept the detected engine or select a different local Docker context or absolute Unix socket. Show the resolved endpoint before saving. Resolve the selected context to its local socket and pass `DOCKER_HOST=unix:///…` only to the installation's child processes. Save the selection and local daemon identity. Revalidate before resuming the installation. If a saved context changes or its engine disappears, show the problem and keep existing data on its original engine. Preserve Docker’s global current context. Reuse 003’s engine and Compose checks, including the refusal of TCP and SSH engine endpoints. On macOS the runtime manager keeps its socket inside the engine VM. [Engine implementation](../../cli/src/engine.ts)

Use the matching packaged CLI from a Finder launch without requiring npm, a terminal or an existing `your-space` command on PATH. Fresh desktop installations prefer loopback port 8081. When another program holds that port, the CLI selects an available port and reports the workspace address. Reuse the app-managed installation folder or initialize an empty one with the packaged release files and `init --this-machine`. Run the CLI in JSON mode with `start --defer-owner --no-open` to check owner state before asking for a name. If another installation or a port conflict prevents startup, explain what the owner can do and allow retry. Reopening reuses the folder and its data. [003 CLI contract](../003-install-with-the-cli/contracts/cli-commands.md)

If the server has an owner, open its normal sign-in page or resume its existing session. For an unclaimed local installation, collect the owner's name and username and pass them to the existing CLI owner-creation flow. Open its short-lived, single-use set-password link in the chosen workspace, then let the owner sign in. Validate the origin and path before using the link and keep its fragment out of logs, diagnostics and saved connection settings. Use the existing operator recovery flow if a setup link expires. If another operator has claimed the installation, return to sign-in. [001 owner commands](../001-workspace-owner-access/contracts/operator-commands.md)

**Connect to a server.** Enter the existing workspace’s canonical HTTPS address, including a proxy or custom domain. HTTP is also supported for a loopback workspace on the same computer. Accept the existing `/api/status` response and open the web workspace. An incompatible response should identify the address as unsupported. Docker, Compose and local operator commands are unnecessary on this path. An unclaimed remote server shows instructions for its operator. An unreachable server, invalid certificate or storage error gives the owner a retry or an address correction. Keep browser sessions scoped to each workspace. Save each address opened as a connection with a name, reopen the one used last on relaunch, and offer the saved connections in the launcher and the Connections menu ([decision 2026-11-24](../../docs/architecture/decisions.md#first-public-release-audience-and-clients)). [001 HTTP contract](../001-workspace-owner-access/contracts/http-api.md)

**Install the first app.** In **Apps**, paste the link to the app’s kit (since 2026-11-23 every install starts from a kit: in the web client, its link or an entry in the kit directory; the server command also takes a kit file, with or without a Compose file on the server's machine; [Kits define apps](../../docs/architecture/decisions.md#kits-define-apps). Superseded the same day: the kit directory and `install-app --compose` are gone; see the [alpha scope](../../docs/architecture/decisions.md#alpha-scope)). Review the pinned kit, source, images, settings and requested connections. Confirm **Install**, follow the server job and open the running app. This is the existing 002 flow. Local kit-file updates and agent-role grants retain their separate operator and owner controls. [002 installation contract](../002-install-an-app/contracts/http-api.md)

**Close, quit and update.** Closing the window keeps the app in the Dock and a local workspace running; the Dock icon shows the window again. Quitting the app (⌘Q, the app menu or the Dock) stops the local workspace this app started with the bundled CLI's `stop`, while the launcher shows that it is stopping. If stopping fails or takes more than 2 minutes, the app quits anyway and says the workspace may still be running. During logout, restart or shutdown it waits at most 20 seconds and shows no dialog. A workspace opened with **Connect to a server** is never stopped. Opening the app again opens the workspace used last, which starts the local workspace when that is This Mac. [Decision](../../docs/architecture/decisions.md#first-public-release-audience-and-clients)

The packaged app updates itself from the repository's GitHub Releases with electron-updater. **Your Space › Check for Updates…** checks at any time; **Check for Updates Automatically**, on by default, checks shortly after launch and then daily, and turning it off stops every automatic request. An app on an alpha is offered later alphas, betas and stable releases, an app on a beta later betas and stable releases, and a stable app only stable releases; Release draft accepts only alpha and beta prerelease tags. Downloading and restarting wait for the owner; a downloaded update that wasn't installed installs when the app quits. Restarting stops the local workspace first. Each release carries a ZIP of each notarized app and `latest-mac.yml`, which lists their SHA-512 digests, and Squirrel.Mac installs only an app that meets the running app's Developer ID designated requirement. Requests carry no installation identifier. After the app changes version, the next start of the local workspace first runs the bundled CLI's `upgrade --yes --json` with the app's bundled release files (`--release-dir`), as `init` uses them. If that CLI has no `upgrade` command yet, the workspace starts as before; if the installation is newer than the app (`downgrade_refused`), the app says so and doesn't start it. [Release guide](../../docs/maintainers/releasing.md)

## Implementation and acceptance order

1. **Mac shell and remote workspace.** Ship the connection choice and remote path in a private development build. On a Mac without Docker, connect through an HTTPS proxy or domain, sign in and complete the kit installation in the existing UI. Verify that server pages and installed-app content cannot invoke native IPC or CLI commands. Keep privileged setup in the trusted desktop surface.
2. **Local engine and installation.** Drive the local flow with the bundled CLI. Exercise missing and stopped Docker, a functioning default engine, an explicit local engine override and an unsupported remote Docker endpoint. Verify fresh owner creation, existing-owner sign-in, kit installation and reopening the same app and data after quitting. Test with a normal Finder environment.
3. **Qualify the actual download.** Produce a private release candidate with a matching CLI, Compose release files and retrievable images. Record the architecture, macOS, engine, Compose, app, CLI and server versions tested. Prepare separate Apple Silicon and Intel DMGs for GitHub Releases. Sign, notarize and staple the app and the read-only image. Record each final DMG digest. On clean Macs, verify the downloaded images and apps pass signature, ticket and Gatekeeper checks. Drag the app to Applications, eject the image, launch the installed copy and repeat both workspace paths. Private previews use ZIP archives. Record any untested architecture or unavailable release artifact explicitly. Public distribution needs a separate release decision. [Apple notarization guide](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

4. **Close, quit and update.** On Apple Silicon and Intel, close the window and confirm the local workspace keeps running and the Dock icon shows it again. Quit and confirm its containers stop and a server workspace doesn't; log out with the app open and confirm logout isn't held up. Install one signed release from its DMG, publish the next, choose **Check for Updates…**, install and relaunch. Confirm the app reports the new version, the local workspace runs it with its data, and with automatic checks off the app sends no request to GitHub.

[Private preview verification](verification.md) records the completed runs and remaining release checks.
