# Data Model: Workspace Setup and Owner Access

**Feature**: [001 Workspace Setup and Owner Access](spec.md) · **Plan**: [plan.md](plan.md)

All durable state is in one PostgreSQL database on the `ys-postgres` named volume (FR-023). Tables
come from two sources:

- **Better Auth and its organization plugin**, with schema generated by the Better Auth CLI into a
  Drizzle schema file. These are used as the library defines them.
- **Four small Your Space tables** for what no library provides: installation claim state, setup
  codes, actors, and events.

Drizzle Kit generates SQL migrations from both schema files. The server applies them at startup,
and Drizzle records each applied migration in `drizzle.__drizzle_migrations`, which is the schema
version (FR-024). IDs are UUIDs throughout, using Better Auth's `generateId: "uuid"` option.

## How the Spec's Concepts Map to Tables

| Spec concept | Table | Source |
| --- | --- | --- |
| Installation | `installation` (one row) | Your Space |
| Owner account | `user`, with the password hash in `account` | Better Auth |
| Workspace | `organization` | Organization plugin |
| Membership | `member` | Organization plugin |
| Ownership | `member.role = 'owner'` | Organization plugin |
| Session | `session` | Better Auth |
| Setup authority | `setup_code` | Your Space |
| Recovery authority | `verification` (reset token rows) | Better Auth |
| Actor | `actor` | Your Space |

Account, workspace, membership, and ownership stay distinct (FR-014): a user can exist without a
membership, a workspace has members rather than a hard-coded owner column, and ownership is a role
on a membership that spec 004 can extend to other members without touching existing rows.

## Better Auth Tables (used as defined)

- **`user`**: `id`, `name`, `email` (unique), `emailVerified` (always false in this feature,
  FR-007), `image`, `createdAt`, `updatedAt`.
- **`account`**: one `credential` row per user holding the scrypt password hash (`password`).
  Later sign-in methods add rows here without changing `user`.
- **`session`**: `id`, `token` (unique), `userId`, `expiresAt`, `ipAddress`, `userAgent`,
  `activeOrganizationId`, timestamps. Database-backed, so sessions survive restarts (FR-009) and
  deleting the row revokes the session.
- **`verification`**: short-lived tokens, including password reset tokens (30-minute expiry).
  Better Auth consumes a reset token inside the reset transaction, so it works once.
- **`organization`**: `id`, `name`, `slug` (unique), `logo`, `metadata`, `createdAt`.
- **`member`**: `id`, `organizationId`, `userId`, `role`, `createdAt`. This feature creates
  exactly one row, with role `owner`.
- **`invitation`**: created by the plugin and unused until spec 004.
- **`rateLimit`**: Better Auth's rate-limit counters, stored in the database so limits survive
  restarts (FR-011).

## Your Space Tables

### `installation`

Exactly one row, created by the first migration with `state = 'unclaimed'`. Claim state is read
from this row, never inferred from empty tables (FR-013).

| Column | Type | Notes |
| --- | --- | --- |
| `id` | smallint, primary key | Always 1; a check constraint enforces a single row |
| `state` | text | `unclaimed` or `claimed` |
| `workspace_id` | uuid, nullable | References `organization.id`; set when claimed |
| `claimed_at` | timestamptz, nullable | Set when claimed |

Check constraint: `state = 'claimed'` requires `workspace_id` and `claimed_at`, so a claimed
installation can never lack its workspace (FR-004).

State transitions: `unclaimed → claimed` only, inside the claim's final transaction. Nothing in
this feature moves it back.

### `setup_code`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid, primary key | |
| `code_hash` | text | SHA-256 of the normalized code. The code has about 120 bits of randomness, so a fast hash is enough |
| `expires_at` | timestamptz | 60 minutes after issue |
| `failed_attempts` | integer | Locked at 10 |
| `used_at` | timestamptz, nullable | Set in the claim's final transaction |
| `created_at` | timestamptz | |

Issuing a code deletes all earlier unused codes, so at most one code is live. A code is valid when
it is unused, unexpired, and under the attempt limit.

### `actor`

The stable identity that records credit (FR-025). Humans, agents (spec 005), and the server
operator all get actor rows, so records never point straight at `user`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid, primary key | |
| `kind` | text | `human`, `operator`, or later `agent` |
| `user_id` | uuid, nullable, unique | References `user.id` when `kind = 'human'` |
| `created_at` | timestamptz | |

The first migration creates one `operator` actor, used for actions taken from the server's command
line, such as issuing a reset link. The claim creates the owner's `human` actor.

### `event`

A minimal record of setup and recovery actions (cross-cutting scenario 7). The full activity log
is spec 005; it can adopt or extend this table.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid, primary key | |
| `type` | text | `setup.claimed`, `recovery.link_issued`, `recovery.password_reset` |
| `actor_id` | uuid | References `actor.id` |
| `subject_user_id` | uuid, nullable | The account acted on |
| `created_at` | timestamptz | |

Events never store codes, tokens, passwords, or session values (FR-010).

## Claim Sequence

The claim must survive double-clicks, retries, and a crash partway through (FR-004, Story 1
scenarios 6 and 7). It runs under a PostgreSQL advisory lock, so only one claim runs at a time.

1. Take the advisory lock. Read `installation`; if `claimed`, return `already_claimed`.
2. Check the setup code. If it is wrong, increment `failed_attempts` and stop.
3. Remove leftovers from an earlier interrupted claim: before the claim, no user can exist, so any
   `user` rows (with their accounts, sessions, memberships, organizations, and actors) came from an
   attempt that never committed. They are deleted.
4. Create the user and credential with `auth.api.signUpEmail`. The HTTP sign-up route is blocked
   by the allowlist, but the server-side call still works.
5. Create the workspace with `auth.api.createOrganization`, passing the new user's ID. As a
   server-side call it ignores `allowUserToCreateOrganization: false`, and the plugin makes the
   creator a member with the `owner` role.
6. In one transaction: create the human actor, the `setup.claimed` event, mark the code used, and
   set `installation` to `claimed`. This is the commit point.
7. Release the lock, then sign the owner in through Better Auth and return the session cookie.

Before step 6 commits, everything can be discarded and retried. After it commits, the claim is
complete. A retry after a timeout reaches step 1 and gets `already_claimed`, and the client sends
the owner to sign in.

Until the installation is claimed, Better Auth's sign-in rejects every request (a `before` hook),
so leftover accounts from step 4 can never be used. After the claim, a
`databaseHooks.user.create.before` hook refuses to create any user, so no later path can add an
account in this feature.
