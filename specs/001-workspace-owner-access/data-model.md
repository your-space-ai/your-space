# Data Model: Workspace Setup and Owner Access

**Feature**: [001 Workspace Setup and Owner Access](spec.md) · **Plan**: [plan.md](plan.md)

All durable state is in one PostgreSQL database on the `ys-postgres` named volume (FR-023). Tables
come from two sources:

- **Better Auth and its organization plugin**, with schema generated by the Better Auth CLI into a
  Drizzle schema file. These are used as the library defines them.
- **Three small Your Space tables** for what no library provides: whether the owner exists, actors,
  and events.

Drizzle Kit generates SQL migrations from both schema files. The server applies them at startup,
and Drizzle records each applied migration in `drizzle.__drizzle_migrations`, which is the schema
version (FR-024). IDs are UUIDs throughout, using Better Auth's `generateId: "uuid"` option.

## How the Spec's Concepts Map to Tables

| Spec concept | Table | Source |
| --- | --- | --- |
| Installation | `installation` (one row) | Your Space |
| Owner account | `user`, with the password hash in `account` | Better Auth |
| Workspace | `organization` | Organization plugin |
| Membership | `member` | Organization plugin |
| Ownership | `member.role = 'owner'` | Organization plugin |
| Session | `session` | Better Auth |
| Set-password and recovery links | `verification` (reset token rows) | Better Auth |
| Actor | `actor` | Your Space |

Account, workspace, membership, and ownership stay distinct (FR-014): a user can exist without a
membership, a workspace has members rather than a hard-coded owner column, and ownership is a role
on a membership that spec 004 can extend to other members without touching existing rows.

## Better Auth Tables (used as defined)

- **`user`**: `id`, `name`, `email` (unique), `emailVerified` (always false in this feature,
  FR-007), `image`, `createdAt`, `updatedAt`.
- **`account`**: one `credential` row per user holding the scrypt password hash (`password`).
  Later sign-in methods add rows here without changing `user`.
- **`session`**: `id`, `token` (unique), `userId`, `expiresAt`, `ipAddress`, `userAgent`,
  `activeOrganizationId`, timestamps. Database-backed, so sessions survive restarts (FR-009) and
  deleting the row revokes the session.
- **`verification`**: short-lived tokens, including password reset tokens (30-minute expiry).
  Better Auth consumes a reset token inside the reset transaction, so it works once.
- **`organization`**: `id`, `name`, `slug` (unique), `logo`, `metadata`, `createdAt`.
- **`member`**: `id`, `organizationId`, `userId`, `role`, `createdAt`. This feature creates
  exactly one row, with role `owner`.
- **`invitation`**: created by the plugin and unused until spec 004.

## Your Space Tables

### `installation`

Exactly one row, created by the first migration with `state = 'unclaimed'`. Whether the owner
exists is read from this row, never inferred from empty tables (FR-013).

| Column | Type | Notes |
| --- | --- | --- |
| `id` | smallint, primary key | Always 1; a check constraint enforces a single row |
| `state` | text | `unclaimed` or `claimed` |
| `workspace_id` | uuid, nullable | References `organization.id` (`on delete restrict`); set when claimed |
| `claimed_at` | timestamptz, nullable | Set when claimed |

Check constraint: `state = 'claimed'` requires `workspace_id` and `claimed_at`, so a claimed
installation can never lack its workspace (FR-004).

State transitions: `unclaimed → claimed` only, set by `create-owner` in the same transaction that
records the event. Nothing in this feature moves it back.

### `actor`

The stable identity that records credit (FR-025). Humans, agents (spec 005), and the server
operator all get actor rows, so records never point straight at `user`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid, primary key | |
| `kind` | text | `human`, `operator`, or later `agent` |
| `user_id` | uuid, nullable, unique | References `user.id` when `kind = 'human'` |
| `created_at` | timestamptz | |

The first migration creates one `operator` actor, used for actions taken from the server's command
line, such as creating the owner or issuing a reset link. `create-owner` also creates the owner's
`human` actor.

### `event`

A minimal record of owner-creation and recovery actions (cross-cutting scenario 7). The full activity log
is spec 005; it can adopt or extend this table.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid, primary key | |
| `type` | text | `owner.created`, `recovery.link_issued`, `recovery.password_reset` |
| `actor_id` | uuid | References `actor.id` |
| `subject_user_id` | uuid, nullable | The account acted on |
| `created_at` | timestamptz | |

Events never store codes, tokens, passwords, or session values (FR-010).

## Creating the Owner

`create-owner` runs these steps in its own process (FR-004):

1. Read `installation`. If it says `claimed`, exit with `owner_exists`.
2. Create the account with `auth.api.signUpEmail` and a random password that is never shown. This
   runs on the command's own Better Auth instance, which has sign-up on. If an account with that
   email already exists from an earlier interrupted run, reuse it.
3. Create the workspace with `auth.api.createOrganization`, passing the user's ID. The plugin makes
   the creator a member with the `owner` role. If the user already owns a workspace from an earlier
   run, reuse it.
4. In one transaction, create the human actor, record the `owner.created` event, and set
   `installation` to `claimed` with the workspace ID. A check constraint means it can never be
   claimed without a workspace.
5. Issue the set-password link with `auth.api.requestPasswordReset` and print it.

If a run stops partway, running it again with the same email reuses what exists and finishes.
