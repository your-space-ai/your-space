# Implementation Plan: Encrypt Your Space's Stored Data

**Spec**: [spec.md](spec.md)

## Summary

A third platform secret, the data key, is generated by the secrets step into `ys-secrets/data/key`
(or set in `.env` as `YS_DATA_KEY`). Apps' settings are encrypted with it instead of a key derived
from the auth secret. When the server starts, before it serves anything, it moves every stored
setting onto the data key in one transaction: values from before it existed, and values a replaced
data key left. No dependency is added; Node's built-in crypto does the encryption, as it already
did for apps' settings.

## Constitution Check

| Principle | How this plan meets it |
| --- | --- |
| II. User control | The data key is generated; the owner can set it in `.env` instead. Whole-database encryption stays the owner's choice, and the guide says how. |
| V. Protect private data | Apps' secrets are encrypted with a key kept apart from the database; the key is never logged or shown unless asked. |
| VII. Reuse before building | Node's `crypto` (AES-256-GCM, HKDF), as before; no extension, no other PostgreSQL build. |

## Design

| Part | Change |
| --- | --- |
| `server/src/secrets.ts` | `DATA_KEY` (dir `data`, file `key`, 0400, readable by the server only). A missing data key is generated even when the database exists: the server reports any app whose settings it can't read instead of refusing to start. `--new data-key` keeps the replaced key as `data/previous` until `--forget previous-data-key` removes it. |
| `server/src/commands/secrets-step.ts` | `--forget previous-data-key`. |
| `server/src/config.ts` | `dataKey` and `previousDataKey`; `YS_DATA_KEY` is a known setting. |
| `server/src/apps/settings.ts` | `v2` values: AES-256-GCM with a key derived (HKDF) from the data key. `v1` values, from the auth secret, are only read, to move them. |
| `server/src/apps/keys.ts` | `moveSettingsToDataKey`: at start, in one transaction, re-encrypts `v1` values and values on the previous data key; counts and leaves values no key can read. |
| `server/src/apps/service.ts` | Uses the data key. A setting no key can read stops the app's next apply with "remove the app, keeping its data, and install it again". |
| `server/src/index.ts` | Runs the move before serving, and stops if it fails. |
| `deploy/stack.yaml` | Passes `YS_DATA_KEY` to the secrets step and the server. |
| `cli/` | `secrets replace data-key`: the secrets step, a server restart (which re-encrypts), then `--forget previous-data-key`. The auth-secret warning about apps goes. |
| `docs/install/README.md` | "Secrets" lists three; "What Your Space Encrypts" is new; "Replace a Secret" and "Lost Secrets" describe the data key. |

The order of keys tried when moving a value: the data key (already moved), the previous data key, then
the auth secret for a `v1` value. A value only the previous key reads is re-encrypted, so the next
start finds nothing to move and the previous key can be forgotten.

## Testing

- `server/tests/data-key.test.ts`: moving `v1` values, replacing the auth secret afterwards, moving
  from a previous data key, and an unreadable value left as it is.
- `server/tests/secrets.test.ts`: the data key is generated, kept, generated next to an existing
  database, kept as previous on replacement (and not overwritten by a second one), forgotten, and left
  to `.env`.
- `server/tests/config.test.ts`: the data key and the previous one are read.
- `e2e/tests/cli.spec.ts`: with an app installed, replacing the auth secret, the database password and
  the data key leaves the app running with the same generated `API_TOKEN`, and the previous data key
  is gone.
