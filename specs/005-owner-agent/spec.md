# Journey 005 · Give my agent scoped access to an app

**Journey specification · 2026-11-21.** See the [delivery checklist](tasks.md) for tested behavior and outstanding acceptance. [Plan](plan.md) · [Tasks](tasks.md) · [Integration findings](research.md) · [Acceptance walkthrough](quickstart.md)

## Owner review

“I choose what my agent can do in one installed app. I can see what it changed, decide when to approve a request, and withdraw access.”

In the web dashboard, create a named agent, choose an installation and any number of eligible roles from its pinned installation kit, and issue a key. Supply the key in that agent’s environment. The agent uses the Your Space CLI against your server. Return to the dashboard to inspect what ran, narrow its grant, rotate its key or disable it.

**First acceptance flow.** List synthetic records, create one and edit that same record through routes declared by the installed kit. The kit defines its role names and supported operations. For each permitted operation the owner chooses whether a request runs directly or waits for approval.

**Scope for review.** Extend installation kits, qualify one independent integration and verify the owner journey with a real external agent. A second neutral catalog tests portability. Keep the selected app, agent environment and domain-specific acceptance data in the local test plan. [Qualification criteria](research.md)

## User scenarios and acceptance

1. **Give my agent a key.** Starting with an existing owner workspace, create a named agent and issue a credential. The clear value is shown once. A valid credential with zero grants can perform no app action. Two credentials can be distinguished and revoked independently. Changing a name preserves identity and history.
2. **Choose exactly what it can do.** The owner sees eligible role IDs and descriptions for a specific installation. Show the allowed HTTP methods and routes for each role in plain language. Save any subset of kit roles enabled by the owner in Your Space for that installation. An owner with installation-operator access can upgrade a matching local version 1 kit in place to add agent route declarations while retaining the same app and data. An unsupported app remains usable in its pane and has no selectable agent roles. App installation and agent creation grant nothing. A kit role enabled later gives the agent nothing automatically.
3. **Make a change.** Give the external agent a grant for the kit’s list, create and edit routes. Have it list records, create one synthetic record and edit a single field. Verify in the app that its ID is unchanged, the requested value persisted and unrelated fields were preserved.
4. **Restrict or stop the agent.** Switch to read-only while the agent is running. The next read succeeds and the next write is denied with no app change. Revoke one credential and verify another still follows the same grants. Disable the identity and every credential stops. Reinstalling an app creates a fresh authorization boundary.
5. **Understand the result.** As owner, see action, installation, actual agent, delegating owner, time, outcome and a request ID. Open the connected app to see its resulting state. App errors, denied requests and uncertain write outcomes are distinguishable. Unauthenticated attempts never acquire an invented agent identity.

6. **Choose when to approve.** For this agent and installation, use the kit’s recommended settings, switch on “ask for all writes”, or set individual routes to Ask or Allow. Show a pending request in the dashboard with the agent, app, action and exact proposed change. Approve one edit and see it applied once. Reject another and see the existing task unchanged. Both the grant and approval policy are visible when editing access.

## Requirements

- **FR-01 · Identity.** Only an authenticated owner may manage agents, credentials and grants. Bind every agent to its owner and workspace. Persist agent actors separately from humans. Preserve attribution after revocation, app removal and restart.
- **FR-02 · Credential lifecycle.** Generate high-entropy opaque keys, persist only verifiers and safe identifiers, and disclose a new key once. Rotation atomically replaces one key while preserving grants and other keys. An owner who misses the disclosure can issue a replacement. Never return key material in list responses, activity, logs or command arguments.
- **FR-03 · Real owner authority.** The owner connects a scoped app API credential to one installation. The upstream app enforces that credential’s native scope on every call. In Your Space the owner enables kit roles for delegation; these restrict which routes the gateway may call using that credential. Kit roles need no corresponding upstream roles. Store the credential encrypted, verify the binding, and fail closed when it is unavailable.
- **FR-04 · Revocation.** Check active identity, key, installation binding, enabled kit roles and current grants on each request. Removing an enabled kit role transactionally withdraws dependent grants in Your Space. Re-enabling it requires explicit regrant. Disabling or replacing the app credential invalidates its previous binding and outstanding approvals. The app still rejects calls when its credential has expired, lost native access, or been revoked. A request already admitted may finish; display its real outcome.
- **FR-05 · App contract.** An opted-in installation reads its catalog from a versioned, strictly validated kit. Each role lists allowed method/route pairs via stable route IDs. Effective permissions are the union of the agent’s currently granted roles in that installation, limited by the owner binding and native app authority. Each route declares input, allowed output, effect and recommended approval. Select the app by installation ID. Your Space checks the method and matched route, obtains the bound app credential only at dispatch, and supplies it server-side to the pinned internal app endpoint. The app enforces its native authorization. The gateway records the actual agent and delegator; an integration needing native agent attribution must prove that capability independently. Use only positive, safely delegable roles for this version.
- **FR-06 · Generic CLI and gateway.** Discover supported actions and invoke by installation and action ID. Never proxy caller-selected URLs, arbitrary HTTP methods or paths. Publish only named, validated actions. Any remote gateway connection uses HTTPS. Ignore owner cookies on agent calls and strip untrusted identity headers. Use the installation’s authenticated internal action route even when its human-facing interface has a published URL.
- **FR-07 · Mutations.** The integration accepts a stable operation ID for each logical write. Persist the result or an app-side receipt atomically with the write; duplicate delivery returns the same result, and reuse with different input conflicts. Updates require an expected app revision. After a timeout, reconcile by operation ID before reporting success or retrying. Preserve unrelated fields and history. The app owns domain semantics and conflict detection.
- **FR-08 · Records.** Establish a durable invocation record before dispatch. Keep agent identity and owner distinct through app enforcement. Correlate the app receipt and the owner-visible activity entry. Record bounded metadata and a safe result reference; keep credentials, raw app rows, record contents, arguments, model prompts and response bodies out of logs. Page owner reads.
- **FR-09 · Isolation and portability.** Role names, routes, resource fields and application behavior come from the independent integration. The same platform binary and CLI must work with a second unrelated catalog and installation. Core tests use neutral fixtures.
- **FR-10 · Existing installs.** Additive migrations preserve owner setup, sessions and installed apps. Existing installations without an agent integration remain browser-only. Uninstall invalidates grants and routes for that installation while preserving audit history. Never delete provider data as a side effect of revocation.

- **FR-11 · Approval policy.** Owner settings apply per agent and installation. When “Ask for all writes” is on, every write requires owner approval even if its route is set to Allow. Otherwise the explicit route setting wins, then the reviewed kit recommendation; absent a recommendation ask on writes and allow reads. The owner can explicitly require approval for a read. A write-capable method always counts as a write, and a kit may classify another route as mutating. Multiple roles granting one route cannot weaken the effective policy. Installing a kit, selecting a recommendation or approving one request cannot grant a route.
- **FR-12 · Exact review.** Persist pending requests before contacting the app. Show only the owner a safe preview of the validated parameters, including the actual proposed change. Keep that access-controlled payload encrypted and short-lived, separate from activity logs. Approval/denial is owner-only and bound to the agent, key, installation, kit revision, method, route, normalized input and operation ID. Expiry, rejection or a stale binding is terminal. Recheck credential, grant, owner authority, approval policy, kit and resource revision before dispatch. Retries or concurrent decisions cannot apply a write twice. A pending request still requires a decision if the owner later relaxes policy.
- **FR-13 · Kit trust and secrets.** Show origin, pinned revision or local digest, exact role permissions and recommended settings before acceptance. A vetted community preset identifies the review source and exact revision; a local or unreviewed kit carries no vetted badge. The owner may override recommendations. Accepting a changed kit cannot silently add routes to an existing grant or relax approvals. Agent clients receive only normalized allowlisted results. The underlying app credential is never exposed to an agent, preview, response, error, log or tool environment.

## Done when

All six scenarios pass against one identified release candidate. The check includes two distinct agents, two installations, same-session role and credential changes, concurrent requests and a retry after a lost response. Verify a real external invocation and an independent read of the resulting synthetic record in the installed app. Run the CLI against both a local gateway and an HTTPS server. Retain sanitized versions, IDs and outcomes. Scripted conformance results and actual integration evidence are recorded separately.

**Outside this journey:** hosted agent execution, external agent provisioning, syncing app data into core, general-purpose SDKs, team membership, generic UI single sign-on, connectors to arbitrarily hosted services and automated execution schedules. The owner supplies a running Docker workspace, an installed integration and an external agent environment.
