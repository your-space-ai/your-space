# Journey 005 · Let my agent manage a recurring task

**Draft for owner review · 2026-11-21.** This is an implementation specification. All slices and verification remain open. [Plan](plan.md) · [Tasks](tasks.md) · [Integration findings](research.md) · [Acceptance walkthrough](quickstart.md)

## Owner review

“I give my Buzz agent access to one installed app. I ask it to schedule a weekly chore and later to change the weekday. I see the same task and its new schedule in DoneTick, and I can take that access away in Your Space.”

In the web dashboard, create a named agent, choose an installation and a subset of your app roles, and issue a key. Supply the key in that agent’s Buzz environment. The agent uses the Your Space CLI against your server. Return to the dashboard to inspect what ran, narrow its grant, rotate its key or disable it.

**Proposed first slice of recurring-task management:** list the owner’s recurring tasks, create a weekly task, and edit that task’s weekly schedule. Support one named weekday and local time in the owner’s configured time zone. Leave completion, deletion, assignment to other people and broader recurrence patterns for subsequent work. Creation and edits under a management grant take effect directly. Choosing a read-only grant permits listing alone.

**Scope for review:** one general integration contract, one independent app integration and one real Buzz run with synthetic tasks. The platform stays app- and runtime-agnostic. A small conformance fixture demonstrates portability. DoneTick’s external API cannot express the full example; first prove a supported app-side route. A maintained fork, paid dependency or larger upstream change calls for an owner decision before taking it on. [Evidence](research.md)

## User scenarios and acceptance

1. **Give my agent a key.** Starting with an existing owner workspace, create a named agent and issue a credential. The clear value is shown once. A valid credential with zero grants can perform no app action. Two credentials can be distinguished and revoked independently. Changing a name preserves identity and history.
2. **Choose exactly what it can do.** The owner sees eligible role IDs and descriptions for a specific installation. Save only an exact subset of roles explicitly assigned to the owner there. An unsupported app remains usable in its pane and has no selectable agent roles. App installation and agent creation grant nothing. A human role added later gives the agent nothing automatically.
3. **Make a recurring change.** The owner supplies the Your Space URL and one agent key to a Buzz environment. With a management grant, ask it to create “Water the test fern” every Monday at 09:00, then change the same task to Wednesday at 09:00. Reopen DoneTick and verify the same task ID, weekly rule, next due date and original completion history. A one-off due date change fails acceptance.
4. **Restrict or stop the agent.** Switch to read-only while the agent is running. The next read succeeds and the next write is denied with no app change. Revoke one credential and verify another still follows the same grants. Disable the identity and every credential stops. Reinstalling an app creates a fresh authorization boundary.
5. **Understand the result.** As owner, see action, installation, actual agent, delegating owner, time, outcome and a request ID. Open the connected app to see its resulting state. App errors, denied requests and uncertain write outcomes are distinguishable. Unauthenticated attempts never acquire an invented agent identity.

## Requirements

- **FR-01 · Identity.** Only an authenticated owner may manage agents, credentials and grants. Bind every agent to its owner and workspace. Persist agent actors separately from humans. Preserve attribution after revocation, app removal and restart.
- **FR-02 · Credential lifecycle.** Generate high-entropy opaque keys, persist only verifiers and safe identifiers, and disclose a new key once. Rotation atomically replaces one key while preserving grants and other keys. An owner who misses the disclosure can issue a replacement. Never return key material in list responses, activity, logs or command arguments.
- **FR-03 · Real owner authority.** An approved integration binds a verified app principal to the workspace owner and supplies that principal’s actual delegable role IDs for this installation. Link through a deliberate owner action with proof from the app. Verify this binding and current roles before accepting grants and dispatching actions. Workspace ownership or a role catalog alone cannot establish app authority. Unsupported role semantics or an unavailable authority check fail closed.
- **FR-04 · Revocation.** Check active identity, key and grants on each request, including an existing client session. Prune revoked owner roles from delegated grants. Restoring the owner role must require explicit regrant. The integration must communicate or version role removals so a remove-then-restore between requests cannot revive an old grant. Deny revoked catalog roles and stale grant edits. A request already admitted may finish; display its real outcome.
- **FR-05 · App contract.** An opted-in installation supplies a versioned catalog of roles, action IDs, input shapes and output descriptions through the reviewed integration. Select the app by installation ID. The app verifies the gateway identity envelope, intersects delegated roles with app-local authority, and enforces its normal resource rules on the same backend used by its UI. Use only positive, safely delegable roles for this version.
- **FR-06 · Generic CLI and gateway.** Discover supported actions and invoke by installation and action ID. Never proxy caller-selected URLs, arbitrary HTTP methods or paths. Publish only named, validated actions. Any remote gateway connection uses HTTPS. Ignore owner cookies on agent calls and strip untrusted identity headers. Use the installation’s authenticated internal action route even when its human-facing interface has a published URL.
- **FR-07 · Mutations.** The integration accepts a stable operation ID for each logical write. Persist the result or an app-side receipt atomically with the write; duplicate delivery returns the same result, and reuse with different input conflicts. Updates require an expected app revision. After a timeout, reconcile by operation ID before reporting success or retrying. Preserve unrelated fields and history. The app owns timezone handling, recurrence calculations and conflict detection.
- **FR-08 · Records.** Establish a durable invocation record before dispatch. Keep agent identity and owner distinct through app enforcement. Correlate the app receipt and the owner-visible activity entry. Record bounded metadata and a safe result reference; keep credentials, raw app rows, task titles, arguments, model prompts and response bodies out of logs. Page owner reads.
- **FR-09 · Isolation and portability.** No DoneTick or Buzz branches, vendor IDs, recurrence fields, hostnames, token handling or fallback credentials in platform source, schemas, migrations, defaults or CLI commands. The app integration and packaging live in independent repositories and use the documented interface. Core conformance tests use synthetic identities and neutral actions. A second catalog or installation works without rebuilding the platform. Buzz is an external client used for acceptance.
- **FR-10 · Existing installs.** Additive migrations preserve owner setup, sessions and installed apps. Existing installations without an agent integration remain browser-only. Uninstall invalidates grants and routes for that installation while preserving audit history. Never delete provider data as a side effect of revocation.

## Done when

All five scenarios pass against one identified release candidate. The check includes two distinct agents, two installations, same-session role and credential changes, concurrent requests and a retry after a lost response. Record a real Buzz invocation and a re-read in DoneTick on synthetic data. Run the CLI against both a local gateway and an HTTPS server. Retain sanitized versions, IDs and outcomes. Scripted conformance results and actual integration evidence are recorded separately.

**Outside this journey:** hosted agent execution, Buzz provisioning, syncing personal task data into core, general-purpose SDKs, team membership, generic UI single sign-on, connectors to arbitrarily hosted services and automated execution schedules. The owner supplies a running Docker workspace, an installed integration and an external agent environment.
