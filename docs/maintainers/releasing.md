## What a release ships

| File or package | Platforms | Published to | For |
| --- | --- | --- | --- |
| Server, web and runtime images, tagged with the version | Linux AMD64 and ARM64 | GHCR | Every installation |
| `your-space.tar.gz`, the Compose bundle | Any | GitHub release | `your-space init` and manual installs |
| `your-space-ai-cli-<version>.tgz`, the CLI npm package `@your-space-ai/cli`, with its README and the project's license | Any machine with Node 22.12 or newer | npm, and the same file on the GitHub release | Mac and Linux users with Node, and agents |
| `your-space-linux-x64`, `your-space-linux-arm64`, the standalone CLI | Linux Intel/AMD and ARM64 | GitHub release | Servers without Node |
| `your-space-linux-licenses.txt`, the licenses of Your Space and of the Node runtime and JavaScript packages inside the standalone CLI | Any | GitHub release | Anyone redistributing or reviewing the standalone CLI |
| `your-space-macos-arm64-<version>.dmg`, `your-space-macos-x64-<version>.dmg`, signed and notarized, with the CLI inside | macOS Apple Silicon and Intel | GitHub release | Mac users |
| `your-space-macos-arm64-<version>.zip`, `your-space-macos-x64-<version>.zip`, the same notarized and stapled apps, and `latest-mac.yml`, which lists them with their SHA-512 digests | macOS Apple Silicon and Intel | GitHub release | The Mac app's updater |
| `SHA256SUMS` | — | GitHub release | Checking any download |
| `latest-mac.yml`, which lists the release's update ZIPs by their full links into the release, and `channel.json`, which names its version and commit | macOS Apple Silicon and Intel, and any | The rolling `alpha` prerelease on GitHub, which Release publish points at the newest release | The Alpha channel, from alpha.2: the Mac app and `your-space upgrade --channel alpha` |

Not shipped: `.deb` and `.rpm` packages, standalone macOS CLI downloads, Homebrew, the Linux desktop app and Windows. Add a new download as a new file; keep existing file names (installed Mac apps look for `latest-mac.yml` and the ZIP names it lists, and the `alpha` feed's two files stay at their fixed address), the npm package name `@your-space-ai/cli` (published by the `your-space-ai` npm organization; the command it installs is `your-space`), the image names and the `SHA256SUMS` format stable, because install guides, scripts and the CLI depend on them.

Each piece has its own workflow:

| Workflow | What it does |
| --- | --- |
| [Release draft](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/release-draft.yml) | Checks the tag, runs the workflows below and creates the draft release with `SHA256SUMS` |
| [Release images](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/release-images.yml) | Builds and pushes the versioned images to GHCR, each processor's on a GitHub-hosted runner of that architecture |
| [Release CLI](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/release-cli.yml) | Builds the npm package, the Linux executables and the Compose bundle |
| [Release macOS app](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/release-macos-app.yml) | Calls Build macOS app, then signs and notarizes both DMGs on a GitHub-hosted runner in the protected `macos-release` environment, and makes the update ZIPs and `latest-mac.yml` |
| [Build macOS app](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/macos-app-build.yml) | Builds and install-tests both DMGs without signing, and checks an update ZIP and feed made from each app; also runs on pull requests that touch the desktop app |
| [Release install test](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/release-install-test.yml) | Installs from the built files on fresh Linux x64 and ARM64 runners and installs the npm package |
| [Release publish](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/release-publish.yml) | When the draft is published, installs from the public release without credentials, then publishes the npm package, moves the images' `latest` tag and points the `alpha` feed at the release |
| [Canary](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/canary.yml) | On every push to main, publishes a canary build with Release images, Release CLI and Release install test; see [Canary builds](#canary-builds) |

## Release steps

1. **Merge to main** once CI is green.
2. **Tag the tip of main** with its version (for example `v0.1.0`) and push the tag. The tag must still point to the tip of main when the draft workflow starts. A prerelease is a numbered `alpha` or `beta`, such as `v0.1.0-alpha.2` or `v0.1.0-beta.1`: those are the prereleases the Mac app's updater offers, so Release draft refuses other kinds, such as `rc`, and unnumbered or longer ones, such as `v0.1.0-alpha` or `v0.1.0-alpha.2.1`, after which a canary build wouldn't sort before the next release.
3. **Run Release draft** on main with that tag once every check on that commit has passed, including the ones that run only after the merge: CircleCI's browser tests in Chromium, Firefox and WebKit, and its Arm tests. Release draft refuses to start until every commit status and check run on the tagged commit has passed, and lists the ones that haven't. Skipped and neutral check runs count as passed, as they do for required checks; its own runs, including an earlier failed one, are left out. On a commit that changes only CI configuration (`.github/`, `.circleci/`) or documentation, the browser, Arm and Compose tests stop early or are skipped and count as passed, because the code is an earlier commit's: tag such a commit only once those tests ran and passed on the last commit before it that changed code. It then verifies the tag, pushes the versioned images, builds the CLI files, installs a fresh workspace from them on Linux x64 and ARM64 and resumes it, signs and notarizes both DMGs, opens each notarized app on a Mac of its architecture, checks its update ZIP, and creates a draft GitHub release with the ten files and `SHA256SUMS`. The versioned images are on GHCR at this point; if their packages aren't public yet, make the `your-space-server`, `your-space-web` and `your-space-runtime` packages public in each package's settings. Release publish checks this before npm. A failed run creates no draft; if an upload leaves a partial draft, inspect it before deleting it and retrying.
4. **Review the draft** against the checks below. Mark preview versions as prereleases.
5. **Publish the draft.** Publishing also makes the release visible to installed Mac apps: those that check automatically offer it within a day. An alpha is offered only to apps on an alpha, and a beta to apps on an alpha or a beta. Publishing runs Release publish. It first installs from the published release as a stranger would, on fresh Linux x64 and ARM64 runners with no GHCR sign-in and no token: it downloads every file from the release's public links and checks it against `SHA256SUMS`, reads the three images for AMD64 and ARM64 without signing in, and sets up a workspace with the standalone executable, which downloads the Compose bundle and pulls the images itself. If an image package is still private, this fails with a message saying so; make the packages public and re-run the failed jobs. The release is already public by then, so if the check fails for any other reason, take it back to a draft with `gh release edit <tag> --draft` while you fix the cause. A Mac app may already have installed it, and the updater never offers the same version again, so ship the fix as a new, higher version; delete the draft, move the tag and run Release draft again only for a version that was never published. Only when this check passes does Release publish check the npm tarball against `SHA256SUMS`, publish that exact file to npm (`next` for prereleases, otherwise `latest`) and point the images' `latest` tag at the version (not for prereleases). It stages the version with npm's [trusted publishing](https://docs.npmjs.com/trusted-publishers) and [staged publishing](https://docs.npmjs.com/staged-publishing): the `@your-space-ai/cli` package trusts only this repository's `release-publish.yml`, for staging only, so no npm token is stored. **Approve the staged version** on npm (the package's Staged Packages tab, or `npm stage approve <stage-id>`) with two-factor authentication; until then npm doesn't serve it. If more than one version is staged, approve them oldest first: each keeps the tag it was staged with, so the last one approved holds `next` or `latest`. Before publishing the draft, open the package's settings page on npm and check that it lists a trusted publisher that is not expired and matches exactly: GitHub Actions, this repository, workflow `release-publish.yml`, no environment, and only staging allowed. If none matches, add one with those settings and delete any that don't match. npm expires a new trusted publisher 48 hours after it was added unless a successful stage has validated it, so a publisher added long before a release may need adding again. An npm version can never be reused, so publishing is one-way. Once the stranger check passes, Release publish also points the Alpha channel's feed at the release, never at a release older than the one the feed names: [`deploy/alpha-feed.sh`](https://github.com/your-space-ai/your-space/blob/main/deploy/alpha-feed.sh), run from the release's tag, checks the release's `latest-mac.yml` against its `SHA256SUMS` and uploads, to the rolling `alpha` prerelease, a copy that lists the update ZIPs by their full links into the release, then `channel.json`, which names the release, each checked once it is there. It creates the `alpha` prerelease the first time, and changes nothing when the feed already names this release or a newer one, so publishing an older release after a newer one leaves the feed on the newer. It reads both files, so a newer release's job that stopped between its two uploads, leaving `latest-mac.yml` on that release and `channel.json` behind, also keeps an older release out; the job says in a warning which release's **alpha-feed** job to re-run to finish. While a file is replaced it is missing for a moment, so a Mac app on Alpha that checks then says it couldn't check. npm and the images don't wait for it. GitHub's server errors are tried again, and **Re-run failed jobs** finishes a run that still fails. One **alpha-feed** job runs at a time and GitHub keeps only one waiting, so when a third release is published while one job runs and another waits, the waiting one is cancelled: if its release is the newest, re-run that job from its Release publish run. A release taken back to a draft after its **alpha-feed** job ran stays named by the feed, which never moves back, so Alpha apps and `upgrade --channel alpha` can't download its files until it is published again or a newer release is. The release keeps its own `latest-mac.yml`: the alpha.1 app finds releases through the releases Atom feed, as before, skipping the `alpha` and `canary` tags.
6. **Check the result from a clean machine:** install with `npx @your-space-ai/cli@<version>`, with a Linux executable and with a DMG, and confirm each reports the version. Check that `curl -fsSL https://github.com/your-space-ai/your-space/releases/download/alpha/channel.json` names the version, and that each link in the `alpha` release's `latest-mac.yml` downloads the update ZIP it lists. On a Mac with an earlier release installed that is offered this one (an earlier alpha for an alpha, an earlier alpha or beta for a beta, any earlier release for a stable release) and a local workspace running, choose **Your Space › Check for Updates…**, install the update and confirm the app and its workspace report the new version. When no earlier release that carries the updater is offered this one, as for the first release that carries it, its DMG install is the check.

When you review the draft at step 4, start its body with the version's hand-written notes from `docs/maintainers/release-notes/` (for example [0.1.0-alpha.1](release-notes/v0.1.0-alpha.1.md)), with the tested platforms filled in, above the generated list of changes.

## Canary builds

The Canary workflow publishes every push to main, so main can run before a release ([Run the canary build](../install/canary.md)). Its version comes from [`deploy/canary-version.sh`](https://github.com/your-space-ai/your-space/blob/main/deploy/canary-version.sh): the nearest version tag in the commit's history, then `canary`, the build's UTC date and the workflow's run number, such as `0.1.0-alpha.1.canary.20261125.42`; after a stable release such as `0.1.0`, the next patch's `0.1.1-0.canary.20261125.42`. It sorts after that release and before the next, so `upgrade` moves installations onto a canary and on to the next release. It builds and pushes the images under that version and makes the CLI files and Compose bundle with Release images and Release CLI, then installs from them with Release install test. Only when that passes does it replace the files of the one `canary` prerelease in place. `SHA256SUMS` and `channel.json`, which names the build's version and commit ([`deploy/channel-json.sh`](https://github.com/your-space-ai/your-space/blob/main/deploy/channel-json.sh)), are deleted before any upload and uploaded last: `SHA256SUMS` once the other files are there, and `channel.json` once the prerelease holds exactly this build's files and its `SHA256SUMS` downloads unchanged. Only once `channel.json` downloads unchanged too does it point the images' `canary` tag at the build, so the images never run ahead of the files installs read. Each canary workflow checks and deletes only its own files on the prerelease; this one's are the Linux files, `SHA256SUMS` and `channel.json`. No canary release may carry `latest-mac.yml`, the file an Alpha Mac app reads, so if the prerelease holds one, the run stops before changing anything: find which workflow uploaded it, delete it, then re-run. It moves the `canary` git tag to the build's commit when GitHub lets the workflow's token do so, and otherwise leaves it with a warning in the run: installs read only the files, and the notes name the commit. One build runs at a time and always finishes; pushes in the meantime wait, and only the newest waiting one runs. A build that would replace a newer one, such as a re-run, leaves the prerelease and the images alone. When GitHub answers a call with a server error, or can't be reached, the call is tried again, up to five times over about two and a half minutes. Each step looks at what an earlier attempt left before it changes anything, so a run that still fails can be re-run: **Re-run failed jobs**, within the week its CLI files are kept, finishes the publish job from where it stopped. A run that fails after it deletes `SHA256SUMS` and `channel.json` and before it uploads them again leaves the prerelease without them, so installs and upgrades from it stop with nothing changed until the re-run finishes.

A canary is never a release, and none of this is a step of one:

- It never moves `latest`, publishes nothing to npm and builds no Mac app, so it needs none of the release secrets or the `macos-release` environment.
- Neither rolling tag, `canary` nor `alpha`, is a version, so the alpha.1 Mac app's updater skips both prereleases, and GitHub never counts a prerelease as the latest release. Release publish runs only for `v` tags, and the GitHub token that Canary and Release publish write with starts no workflow anyway.
- Release draft leaves Canary's check runs out of its gate, as it does its own, and starts the generated notes at the previous version tag.
- The rolling prereleases need their files replaced, and `canary` its tag, so they work only while the repository's immutable releases setting stays off: for the `alpha` feed as for `canary`.

## The unscoped your-space and your-space-ai packages

The npm names `your-space` and `your-space-ai`, without a scope, are for two small packages from [`npm/your-space`](https://github.com/your-space-ai/your-space/tree/main/npm/your-space) and [`npm/your-space-ai`](https://github.com/your-space-ai/your-space/tree/main/npm/your-space-ai), so nobody else can publish code that runs as `npx your-space` or `npx your-space-ai`. Both were published on 2026-11-23 at version 0.0.1, so the names are taken. Each package's command, named after the package, runs nothing: it prints that Your Space is published by the [`your-space-ai` organization](https://www.npmjs.com/org/your-space-ai), the pinned `npx @your-space-ai/cli@<version>` install and a link to the installation guide, then exits with status 1. npm also refuses new names that differ from them only in punctuation, such as `yourspace`, `your_space` and `yourspaceai` ([npm's rule](https://blog.npmjs.org/post/168978377570/new-package-moniker-rules)).

The release workflows don't publish them: Release publish's trusted publishing is set up for `@your-space-ai/cli` only. A maintainer published both by hand from a checkout of main, signed in to npm on an account with two-factor authentication:

```sh
npm whoami
cd npm/your-space
npm pack --dry-run           # bin.js, LICENSE, README.md and package.json, nothing else
npm publish --access public
cd ../your-space-ai
npm pack --dry-run           # the same four files
npm publish --access public
```

`npm pack` and `npm publish` first copy the project's license into each folder. The packages don't depend on the CLI or its version, so they only need republishing when the message, README or a link changes, after raising `version` in that package's `package.json`, since an npm version can never be reused. To publish them from a workflow instead of by hand, add a trusted publisher for each package on npm first.

## Sign the Mac app

Signing runs on a GitHub-hosted macOS runner, never on a maintainer's machine, in a job bound to the protected `macos-release` environment. Only Release draft reaches it, and nothing in the signing workflow runs on pull requests, so code from a fork never sees its secrets. The environment requires the owner's approval and only accepts deployments from `main`, so a draft waits for that approval before it signs. It holds five secrets:

| Secret | Contents |
| --- | --- |
| `MACOS_CERT_P12_BASE64` | The Developer ID Application certificate and its private key, as a base64-encoded `.p12` |
| `MACOS_CERT_PASSWORD` | The `.p12` export password |
| `APPLE_API_KEY_P8_BASE64` | An App Store Connect Team API key with the Developer role, as a base64-encoded `.p8` |
| `APPLE_API_KEY_ID` | That key's ID |
| `APPLE_API_ISSUER` | Its issuer ID |

Protect the environment with the owner as required reviewer and deployments limited to `main`, and store the secrets on the environment only, not on the repository. The job imports the certificate into a temporary keychain with a random password, decodes the API key to the runner's temporary folder, and deletes both when it ends, whether it succeeds or not.

If a secret leaks, revoke what it exposes and replace every secret that belongs to it. For the certificate, ask Apple to revoke it by emailing product-security@apple.com (Developer ID certificates can't be revoked from the developer account), create a new Developer ID Application certificate, and replace `MACOS_CERT_P12_BASE64` and `MACOS_CERT_PASSWORD`. Revoking it means DMGs signed with it can no longer be installed, and copies already installed may stop opening. Recover by publishing a new release, signed and notarized with the new certificate, with its own `SHA256SUMS`; remove the old DMGs from earlier releases, and tell people to download and reinstall the new version. For the API key, revoke it in App Store Connect under Users and Access › Integrations, create a new one, and replace `APPLE_API_KEY_P8_BASE64` and `APPLE_API_KEY_ID`; `APPLE_API_ISSUER` stays the same.

The release job signs the app and its nested code with Developer ID and hardened runtime. Before the first submission to Apple, it runs the app's CLI under that signature and checks the version it reports, on the runner's own Apple Silicon only, so a signature that stops the CLI from starting fails in minutes rather than after Apple's review. It runs a copy of the CLI as the unprivileged `nobody` user with an empty environment, so the CLI can't reach the job's keychain, API key or secrets; **Build macOS app** runs the same check on pull requests. It then notarizes and staples the app, zips the stapled app for the in-app updater, packages the stapled app and an Applications shortcut in a read-only DMG, signs the image, and submits the image to Apple for notarization. After stapling and assessing the final image and checking the app it contains, a job without the signing secrets installs each DMG on a Mac of its architecture, Apple Silicon and Intel: the image and the installed app must pass Gatekeeper with their stapled tickets, the packaged native smoke test opens the app, and its CLI must report the version. The Intel CLI first runs under its release signature there, after notarization. The same job checks each update ZIP: `latest-mac.yml` must list it with its digest and size, and the app it holds must have the version, the Developer ID signature Squirrel.Mac requires to install an update, a stapled ticket and Gatekeeper's approval. If any of these checks fails, the run stops without a draft; otherwise the workflow attaches both DMGs, both update ZIPs and `latest-mac.yml` to the draft release.

The app updates itself with [electron-updater](https://github.com/electron-userland/electron-builder/tree/master/packages/electron-updater), bundled into `app.asar` with its packages' notices in `Contents/Resources/licenses/Updater-NOTICES.txt`. It reads `Contents/Resources/app-update.yml` (this repository's releases) and GitHub's release feed, then downloads `latest-mac.yml` and the ZIP for its architecture from the release. The first release that carries the updater still has to be installed by hand from its DMG; earlier builds can't update themselves.

A new Apple team's first submissions can be held for review for hours or longer, so the signing job may run for six hours, GitHub's limit for a hosted job. If it times out or waits too long for the environment's approval, re-run the failed jobs: the unsigned DMGs it signs and the CLI files are kept for seven days, so a re-run within that time doesn't rebuild them. `xcrun notarytool history` lists the team's submissions and their status.

The packager puts the launcher in `Contents/Resources/app.asar` and records its SHA-256 header digest in the app’s signed property list. Electron requires this archive and checks its integrity. The build disables Electron’s RunAsNode mode, Node environment options and Node inspector command-line switches. After extracting a candidate built with the [Mac source steps](../install/macos-desktop.md#build-from-source), run `node desktop/scripts/seal-macos.mjs verify "/path/to/Your Space.app"` from the same checkout to verify the five fuses, the header digest and each bundled launcher file. The packaged native smoke opens a test workspace through the browser debugging protocol on loopback.

The **Build macOS app** workflow builds, packs and install-tests an Apple Silicon and an Intel candidate on pull requests that touch the desktop app or what it bundles; those runs keep no download. To exercise installation on the target architecture with a local candidate, extract the preview app, run `desktop/scripts/create-dmg.sh "/path/to/Your Space.app" candidate.dmg`, then run `desktop/scripts/test-dmg-install.sh candidate.dmg arm64` (or `x64`). The install test uses a disposable destination and launches the copy after ejecting the image. Add the version as a third argument to check the installed CLI reports it, and `--notarized` before the image to require Gatekeeper's approval of a released DMG.

## Install the candidate

- Follow the [headless installation guide](../install/index.md) on a local machine and a server. Check that the CLI and Compose files select the matching images. Exercise the images on ARM64 and AMD64. Claim the workspace, sign in, restart with storage retained and recover the owner. Open the dashboard on localhost, behind an existing proxy and at a domain with a real certificate.
- Follow the [Mac installation guide](../install/macos-desktop.md) on Apple Silicon and Intel hardware. For each DMG, verify its checksum, the Developer ID signatures, stapled notarization and Gatekeeper assessments for the image and app. Drag the app into Applications in Finder, eject the image, then launch the installed copy and verify its CLI.
- With a local workspace running, close the window and confirm the workspace keeps running and the Dock icon shows it again; quit and confirm its containers stop. With **Check for Updates Automatically** off, confirm the app sends no request to GitHub.
- Try the detected Docker engine, an owner-selected alternative and recovery from a missing or stopped engine. On a Mac without Docker, sign in to an existing HTTPS workspace. From each desktop path, apply a kit and open the installed app. Keep the [private preview results](https://github.com/your-space-ai/your-space/blob/main/specs/008-desktop-entry/verification.md) identifiable by their tested version and hardware.

## Exercise the owner journeys

- Install an independent app from its real source. Review the pinned images and kit revision, confirm installation and verify app limits, network isolation and persistent storage. Follow the [app installation acceptance checks](https://github.com/your-space-ai/your-space/blob/main/specs/002-install-an-app/tasks.md).
- Grant an external agent kit-defined roles. Use synthetic data to list records and read one that the kit asks the owner to approve, through the gateway. Check approval, denial, attribution and the upstream result. Try an ungranted action, change the role, rotate the credential and revoke access. Follow the [agent access specification](https://github.com/your-space-ai/your-space/blob/main/specs/005-owner-agent/spec.md).
- Run [agent-led setup](../install/agent-setup.md). [Install apps](../apps/install-apps.md) from a kit in a public repository by its link, and from a kit file with the server command, `install-app --kit -`.
- Exercise the [roadmap’s appearance and layout journeys](../roadmap.md#dashboard-and-desktop). Test keyboard navigation, focus, labels and error recovery during setup and in the dashboard at the screen sizes claimed for release.

## Review and publish

- Run the automated build and behavior checks for the candidate. Review security boundaries for setup, recovery, app isolation and credentials. Check the default network exposure, outbound requests, dependencies and images. Inspect the distributable files and logs for secrets or private data.
- Test and document supported upgrades and rollback with existing data, including what to preserve before a migration. Check that the installation, recovery and troubleshooting instructions match the tested paths.
- Confirm distribution rights and notices for the code, binaries, images and other assets that ship. The npm package carries the project's license, `your-space-linux-licenses.txt` covers the Linux executables, the web image serves its bundled packages' and fonts' licenses at `/licenses/THIRD-PARTY.md`, and the DMG has them in `Contents/Resources/licenses`. Review the [desktop notices](https://github.com/your-space-ai/your-space/blob/main/desktop/THIRD-PARTY.md) and [license and trademark decision](../architecture/decisions.md#project-license-and-business-model).
- Give the owner the candidate reference, checks performed, open blockers and limitations for a release decision. With approval, publish the reviewed draft. [Release draft](https://github.com/your-space-ai/your-space/blob/main/.github/workflows/release-draft.yml) prepares the draft before publication. Verify that GitHub Releases serves the matching install files, DMGs and checksums, and that npm serves the matching package. Record the release URL, tested versions and unsupported configurations in the release notes.

The Linux rehearsal uses Docker’s [setup-docker-action v5.7.0](https://github.com/docker/setup-docker-action/tree/3f1ab1ab0e29231562e4db4ca600c1a49653bac6) (Apache-2.0) to provide Docker Engine 29.10.0 on disposable hosted runners. This keeps the install test above the product’s minimum supported engine version.
